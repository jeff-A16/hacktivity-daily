Nextcloud 预约日历：未登录者可在任意时间（含过去、非工作时段）强行预约（Unauthenticated attacker can book appointments at arbitrary times, including outside availability and in the past）

  • Nextcloud · 低危 (Low) · 业务逻辑漏洞 · 赏金：未公开 · 披露：2026-11-11 · 报告链接
  • 漏洞原理：公开预约接口拿用户提交的 start/end 当作“搜索窗口”，只要窗口里能找到任意一个可预约空档就放行；但最后写进数据库和组织者日历的，却是用户原始提交的 start/end，而不是刚才校验通过的那个空档。“校验的对象”和“保存的对象”不是同一个值。
  • 发现与复现思路：研究者拿到公开预约链接后，正常点一次预约抓包，发现请求里直接带时间戳；于是把 start 改到过去或深夜、end 拉长到覆盖某个真实空档，服务端照样接受并在确认后生成日历事件，顺带绕过了每日预约上限和冲突检查。作者还对照开源代码定位到“校验后仍用原始输入”的那两行。
  • 新手可借鉴：凡是“先挑选/校验、再保存”的流程（预约、优惠券、库存、价格），都试试修改参数让校验仍通过、但保存的值偏离预期；开源项目可以直接读源码找这种不一致。

Essity 旗下会员站：WordPress 作者枚举泄露 12 万用户邮箱（Mass PII Exposure: 120,000+ Consumer Email Addresses Leaked via Author Enumeration）

  • Essity · 严重 (Critical) · 信息泄露 · 赏金：未公开 · 披露：2026-11-10 · 报告链接
  • 漏洞原理：WordPress 默认允许用 /?author=N 按顺序 ID 访问作者页，REST API 的用户列表和作者 RSS 也会公开“显示名”。该站注册流程把用户邮箱直接设成了显示名，于是这些公开渠道一起把 12 万多名会员的邮箱暴露出来，而且作者页没加 noindex，还能被搜索引擎收录。
  • 发现与复现思路：先用二分法试 author ID，找到返回 200 和 404 的分界，估算出用户总数；再抽查不同 ID 段的页面标题，统计出约 98% 都是邮箱；最后交叉验证 /wp-json/wp/v2/users 和作者 RSS 同样泄露。研究者只做小样本抽查来证明规模，没有批量拉取全部数据。
  • 新手可借鉴：遇到 WordPress 站点，作者枚举和 /wp-json/wp/v2/users 是必查项；单独的“用户名泄露”多半不收，但证明它泄露的是大规模个人信息（PII）就能大幅提升严重度。抽样证明规模即可，别真把数据全拖下来。

【经典回顾】Rocket.Chat 链接预览：短链接重定向绕过 SSRF 防护（SSRF via Improper Redirect Validation in Rocket.Chat oEmbed Function）

  • Rocket.Chat · 中危 (Medium) · SSRF · 赏金：未公开 · 披露：2026-06-11 · 报告链接
  • 漏洞原理：聊天里发链接时，服务器会主动访问该 URL 生成预览（oEmbed）。它对用户提交的第一个 URL 做了内网 IP 过滤，但会自动跟随跳转，而跳转后的目标地址不再检查，于是只要套一层外部短链接，就能让服务器访问内网主机并把内容显示在预览里。
  • 发现与复现思路：研究者在测试环境里做了三组对照：发普通外网链接有预览；直接发内网地址被拦截；发一个跳转到同一内网地址的短链接，却成功拿到了内网页面预览。这种“直连被拦、跳转放行”的对比，是证明过滤只校验了第一跳的清晰证据。
  • 新手可借鉴：看到“输入 URL、服务器去抓取”的功能（链接预览、头像 URL、Webhook、导入），直连内网被拦后别放弃，依次试 302 跳转、DNS 解析到内网的域名、IP 的各种写法；用自己的服务器或 Burp Collaborator 先确认服务器会不会发请求。

Basecamp 跨账号 Webhook 劫持：改写/删除他人账号的 webhook（Cross-account webhook takeover: PUT and DELETE on /<account>/webhooks/<id>.json）

  • Basecamp · 高危 (High) · 越权 / 认证缺陷 (IDOR) · 赏金：有赏金，金额未公开 · 披露：2026-10-30 · 报告链接
  • 漏洞原理：写操作接口只检查“这个项目是不是全员可见”，没有核对 webhook 到底属于哪个账号；路径里的账号 ID 填自己的，webhook ID 填别人的，也能改写甚至删除。而读取接口却做了正确拦截，读写校验不一致。
  • 发现与复现思路：研究者用自己名下的两个互不相关账号，发现 webhook ID 是全局递增的；于是把受害者项目切到全员可见，再拿攻击者账号去 PUT/DELETE 受害者的 webhook，并用对照实验（改回仅邀请后被拒）确认条件。
  • 新手可借鉴：测 IDOR 时别只测 GET，同一资源的 PUT/DELETE 往往走另一套鉴权；ID 是否全局共享、路径中的租户 ID 是否被校验，都值得对比。

WordPress.org Openverse 开放重定向：绕过 SSO 白名单（unauthenticated open redirect — str_replace()'s 4th arg is a count, not a limit）

  • WordPress · 中危 (Medium) · 开放重定向 · 赏金：有赏金，金额未公开 · 披露：2026-10-30 · 报告链接
  • 漏洞原理：代码想只去掉路径开头的 /openverse，却误以为 PHP 的 str_replace 第四个参数是次数上限，其实它只是输出计数，结果所有出现处都被删掉。路径经拼接后，“@”前面的部分变成用户信息，真实主机变成攻击者域名。
  • 发现与复现思路：通过审计源码发现这个误用，再构造含重复 /openverse 的路径验证拼接结果；并指出该链接的主机名仍是 wordpress.org，能通过 SSO 登录后跳转的域名白名单，所以不只是“普通跳转”。
  • 新手可借鉴：被项目排除的“纯开放重定向”要先论证安全影响，比如绕过某个现有防护或接到登录流程里；读开源代码时留意“API 用法误解”类 bug。

MariaDB 命令行工具的 SQL 注入：恶意服务器返回的表名被直接拼进查询（MariaDB CLI Utility Issues）

  • MariaDB · 严重度未评级 · SQL 注入 · 赏金：无 · 披露：2026-11-08 · 报告链接
  • 漏洞原理：mariadb-show 等客户端工具把服务器返回的表名不加转义地拼进后续 SQL，若连接到被攻击者控制的数据库，就可能被诱导执行额外语句。方向与常见 Web 注入相反：被攻击的是客户端。
  • 发现与复现思路：研究者通读客户端源码里用 snprintf 拼接查询的位置，再建一个名字里带反引号和注释符的表，观察工具生成的语句如何被截断改写，同类问题还出现在其他脚本里。
  • 新手可借鉴：“数据来自数据库/服务端，所以可信”是常见盲区，审计时把所有外部来源数据都当作不可信输入；这类 sink 检索（拼接、格式化函数）适合练习代码审计。

WordPress Gutenberg 表单块被滥用为开放邮件中继（Open Email Relay on WordPress Gutenberg Plugin via formAction parameter）

  • WordPress · 未评级 · 业务逻辑 / 滥用功能 · 赏金：已有赏金（金额未公开） · 披露：2026-11-08 · 报告链接
  • 漏洞原理：实验性的 Form 块注册了无需登录的 AJAX 处理函数，并直接信任客户端传来的 formAction 作为收件人；所需 nonce 又被写在公开页面里，任何人都可借该站向任意邮箱发信，用于钓鱼垃圾邮件。

Weblate 的 Qt .ts 文件发现功能存在 XML 实体膨胀（Billion laughs entity expansion in Qt .ts discovery）

  • Weblate · 中危 (Medium) · XML 实体膨胀 / 资源耗尽 · 赏金：未公开 · 披露：2026-11-07 · 报告链接
  • 漏洞原理：解析器处理上传的 .ts 文件时使用默认实体展开，攻击者在 DOCTYPE 里声明嵌套实体并在属性中引用；解析器自带的放大倍数限制挡得住小炸弹，却挡不住接近 1MB 上限的“胖炸弹”，一次解析就消耗大量 CPU。
  • 发现与复现思路：作者先测出小文件会被比例限制拦下，再把文件填充到刚好低于读取上限，让放大比例落在限制之内但绝对工作量很大，并与已有加固提交对比说明漏洞仍在。
  • 新手可借鉴：遇到“已有防护”时，想想防护的度量维度（比例 vs 绝对量），往往能找到绕过；XML 解析点（上传、导入）值得测 XXE/实体膨胀。

curl 在收到 Alt-Svc: clear 后仍把请求发往 HTTP/3 后端（curl 8.23.0 keeps sending requests to an HTTP/3 backend after Alt-Svc: clear）

  • curl · 高危 (High) · 访问控制缺陷 · 赏金：未公开 · 披露：2026-11-07 · 报告链接
  • 漏洞原理：curl 的 Alt-Svc 缓存会记住“某源站可改走 HTTP/3 的另一台后端”。当边缘服务器发出 clear 指令撤销该记录后，curl 在启用持久化缓存时没有清掉这条 H2→H3 的映射，后续请求仍被送往旧的 H3 后端。
  • 发现与复现思路：研究者在本地自建环境，对比 H2→H2 的对照组（会正确清除）与 H2→H3（残留），再让带令牌的请求落到旧后端并被重放，证明凭据可被截获。思路是先找“撤销/过期”类状态机，再做差异对比。
  • 新手可借鉴：“撤销”和“清除缓存”类逻辑常出错；做对照实验、只改一个变量，是写出可信报告的好方法。

OAuth 授权服务器把受害者的凭据发给未经验证的攻击者回调地址（launchpad.37signals.com OAuth AS issues victim-bound credential to unverified attacker redirect → full CIA triad on Basecamp API）

  • Basecamp · 高危 (High) · 认证缺陷 / OAuth · 赏金：未公开（有赏金） · 披露：2026-10-30 · 报告链接
  • 漏洞原理：任何登录用户都能注册 OAuth 客户端并填写任意 redirect_uri，服务端不验证归属或格式；授权时还把绑定受害者身份的令牌（旧版隐式授权甚至直接给 access_token）送到该地址，且允许 http、自定义 scheme、通配符。
  • 发现与复现思路：研究者先注册一个指向自己服务器的客户端，再用另一个账号当“受害者”走授权流程，确认令牌被投递到自己的回调，并用它访问真实 API 验证读写影响。重点是核对 redirect_uri 的校验强度与是否仍开放 implicit 流。
  • 新手可借鉴：测 OAuth 时先查 redirect_uri 的校验（精确匹配？scheme？通配？）和过时授权类型是否仍启用。

已被撤销的协作者在他人操作后重新获得私有评论的访问权（Revoked deployment collaborator regains access to private comments after active collaborator interaction）

  • Vercel · 中危 (Medium) · 访问控制（检查时机错误） · 赏金：$1,026 · 披露：2026-10-29 · 报告链接
  • 漏洞原理：被移除的协作者令牌本来会返回 403，但当另一位仍有权限的协作者在部署工具栏上做一次正常操作后，服务端又把旧令牌当作有效，于是被撤销者能经同步接口拉取私有评论和消息。
  • 发现与复现思路：研究者先邀请再撤销协作者，保留其令牌确认 403；再让有权用户互动，重放旧令牌访问 Replicache 同步接口，发现返回数据。思路是把“权限变更”与“其他用户的状态变化”交叉组合去测试。
  • 新手可借鉴：撤销权限后别只测一次：在别人触发缓存/同步之后再重放旧令牌，常能发现授权状态被覆盖。

WordPress 自定义字段插件：未登录者能读到私密、草稿和加密文章的内容（Unauthenticated Disclosure of Private, Draft, and Password-Protected Post Content via Core Read-Permission Bypass in SCF Reference Fields）

  • WordPress · 高危 (High) · 信息泄露 / 访问控制 · 赏金：有（金额未公开） · 披露：2026-11-05 · 报告链接
  • 漏洞原理：插件的“关联文章”字段取内容时，查询状态设成“任意”，也不检查当前访问者有没有阅读权限。于是 WordPress 核心会返回 404/401 的私密文章、草稿，甚至带明文密码的加密文章，页面渲染时却被原样输出。
  • 发现与复现思路：研究者拿核心的行为当基准（匿名访问返回 404/401），再对比插件的取数函数，发现旧版本只在 AJAX、REST 等入口补了权限检查，渲染路径漏掉了；并证明不需要提交表单，直接写入关联数据也能泄露。
  • 新手可借鉴：看到“之前修过类似漏洞”的补丁，就去找同一功能里没被覆盖的其他入口——补丁不完整是常见的新漏洞来源。

WordCamp 活动站：加密活动的报名名单，换个 REST 接口就能免密码读取（WordCamp Meta gpre: password-protected event RSVP list readable without password via /gpre/v1/.../rsvp-responses）

  • WordPress · 中危 (Medium) · 访问控制缺陷 · 赏金：有（金额未公开） · 披露：2026-11-05 · 报告链接
  • 漏洞原理：官方活动插件的接口会检查“活动是否设了密码、访问者是否已输入”，但站点自己写的封装接口把权限回调设成了“永远通过”，也没复用那个检查，导致匿名者能拿到参会者姓名、用户 ID、主页链接等。
